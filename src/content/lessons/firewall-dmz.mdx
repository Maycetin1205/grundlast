## Was du danach kannst

Nach diesem Kapitel kannst du <Term id="firewall">Firewalls</Term>, <Term id="firewall-regel">Firewall-Regeln</Term>, <Term id="default-deny">Default Deny</Term>, <Term id="allowlist">Allowlisting</Term>, <Term id="dmz">DMZ</Term>, Paketfilter und Application-Layer-Gateways unterscheiden. Du kannst erklären, warum öffentlich erreichbare Server nicht einfach ins interne LAN gehören, wie eine DMZ aufgebaut wird und welche Kommunikationsrichtungen erlaubt oder verboten sein sollten.

Du kannst ausserdem Regelwerke lesen, typische Fehlkonfigurationen erkennen und eine kleine Sicherheitsarchitektur für Webserver, Datenbank und Administrationszugriff begründen. Das ist nicht nur AP1-Stoff, sondern Alltag in Systemintegration, Support, Cloud, Security und Betrieb.

## Warum das wichtig ist

Eine Firewall ist kein magischer Schutzschild. Sie ist eine kontrollierte Grenze zwischen Netzen. Gut konfiguriert reduziert sie Kommunikation auf das, was fachlich benötigt wird. Schlecht konfiguriert ist sie entweder nutzlos offen oder sie blockiert wichtige Dienste und erzeugt Störungen.

Die DMZ ist dabei ein Kernkonzept: Systeme, die aus dem Internet erreichbar sein müssen, werden in ein getrenntes Netzsegment gestellt. Wenn ein Webserver kompromittiert wird, soll der Angreifer nicht direkt im internen LAN mit Clients, Dateiservern, Warenwirtschaft und Datenbank stehen.

<Analogie>
Stell dir ein Firmengelände vor. Das Internet ist die Straße, das LAN sind die internen Büros, die DMZ ist der Empfangsbereich. Besucher dürfen zur Rezeption, aber nicht einfach in die Personalabteilung. Mitarbeitende dürfen zur Rezeption und nach draußen. Zwischen den Bereichen stehen kontrollierte Türen mit klaren Regeln.
</Analogie>

## Grundbegriffe

| Begriff | Bedeutung | Wichtig für Entscheidungen |
|---|---|---|
| <Term id="firewall">Firewall</Term> | System, das Verkehr zwischen Netzen anhand von Regeln kontrolliert. | Entscheidet nach Quelle, Ziel, Port, Protokoll, Zustand oder Inhalt. |
| <Term id="firewall-regel">Firewall-Regel</Term> | Einzelne Erlaubnis- oder Verbotsregel im Regelwerk. | Reihenfolge, Richtung und Default-Regel beachten. |
| <Term id="default-deny">Default Deny</Term> | Standard: alles blockieren, was nicht ausdrücklich erlaubt ist. | Sicherer Grundsatz für professionelle Regelwerke. |
| <Term id="allowlist">Allowlist</Term> | Liste erlaubter Kommunikation. | Besser als "alles erlauben und nur manches sperren". |
| <Term id="paketfilter">Paketfilter</Term> | Filtert nach technischen Paketmerkmalen wie IP, Port und Protokoll. | Einfach, schnell, aber ohne Anwendungskontext. |
| <Term id="stateful-firewall">Stateful Firewall</Term> | Merkt sich Verbindungszustände. | Antworten auf erlaubte Verbindungen werden erkannt. |
| <Term id="application-layer-gateway">Application-Layer-Gateway</Term> | Prüft Verkehr auf Anwendungsebene. | Kann Protokollinhalte verstehen, z. B. HTTP. |
| <Term id="dmz">DMZ</Term> | Separates Netz für öffentlich erreichbare Server. | Trennung zwischen Internet und internem LAN. |
| <Term id="netzsegmentierung">Netzsegmentierung</Term> | Aufteilung eines Netzes in Sicherheitszonen. | Clients, Server, DMZ, Management und Gäste trennen. |

## Firewall-Typen im Vergleich

| Typ | Prüft vor allem | Stärke | Grenze |
|---|---|---|---|
| Paketfilter | IP-Adresse, Port, Protokoll, Richtung | schnell, gut für klare Netzgrenzen | sieht keinen Anwendungskontext |
| Stateful Firewall | zusätzlich Verbindungszustand | erkennt Antworten auf erlaubte Verbindungen | ersetzt keine Inhaltsprüfung |
| Application-Layer-Gateway / Proxy | Anwendungsebene, z. B. HTTP | kann Protokolle verstehen und Inhalte filtern | komplexer, mehr Aufwand, mehr Latenz |
| Personal Firewall | Verkehr eines einzelnen Endgeräts | sinnvoll als Zusatzschutz am Client | ersetzt keine Netz-Firewall |
| Next-Generation Firewall | Kombination aus mehreren Funktionen | App-Erkennung, IDS/IPS, URL-Filter möglich | nur so gut wie Konzept, Pflege und Regeln |

In Auswahl- und Diagnosefällen reicht oft die saubere Unterscheidung:

```text
Paketfilter = schaut auf technische Paketdaten
Stateful = merkt sich Verbindungen
Application Layer = versteht Teile der Anwendungskommunikation
```

<Tipp titel="Stateful in einem Satz">
Eine Stateful Firewall blockiert nicht blind alle eingehenden Pakete. Sie erlaubt Antworten, wenn sie zu einer vorher erlaubten Verbindung gehören.
</Tipp>

## Default Deny und Regelreihenfolge

Ein gutes Firewall-Regelwerk arbeitet nach dem Prinzip:

```text
Erlaube nur, was benötigt wird.
Verbiete den Rest.
```

Das ist <Term id="default-deny">Default Deny</Term>. In BSI-Grundschutz-Sprache entspricht das dem Gedanken, dass nur erlaubte Kommunikation weitergeleitet wird. Praktisch bedeutet das:

| Regel | Quelle | Ziel | Protokoll/Port | Aktion | Zweck |
|---:|---|---|---|---|---|
| 1 | Internet | Webserver-DMZ | TCP 443 | ALLOW | HTTPS zur Website |
| 2 | Webserver-DMZ | Datenbank-LAN | TCP 5432 | ALLOW | nur benötigte DB-Verbindung |
| 3 | Admin-VPN | Webserver-DMZ | TCP 22 | ALLOW | Administration über VPN |
| 4 | DMZ | LAN | ANY | DENY | keine freie Bewegung ins LAN |
| 5 | ANY | ANY | ANY | DENY | Default-Deny-Abschluss |

Die Reihenfolge ist wichtig, weil Firewalls Regeln meist von oben nach unten prüfen. Eine zu breite Erlaubnisregel vor einer Einschränkung kann die spätere Sperre wirkungslos machen.

<Warnung titel="ANY ANY ALLOW ist kein Konzept">
Eine Regel wie `ANY -> ANY -> ANY -> ALLOW` macht eine Firewall als Grenze praktisch wertlos. Wenn so eine Regel für Tests gesetzt wird, muss sie danach wieder entfernt oder streng begrenzt werden.
</Warnung>

## DMZ: Warum Server nicht ins LAN gehören

Eine <Term id="dmz">DMZ</Term> ist ein eigenes Netzsegment für Systeme, die aus nicht vertrauenswürdigen Netzen erreichbar sein müssen. Typische Systeme:

- Webserver oder Reverse Proxy
- Mail-Gateway
- VPN-Gateway
- öffentliche API
- Update- oder Transfer-Server

Das interne LAN enthält dagegen Clients, interne Server, Dateifreigaben, ERP, Drucker, Managementsysteme und oft besonders schützenswerte Daten. Ein Webserver in der DMZ darf deshalb nicht frei ins LAN kommunizieren.

```text
Internet
   |
[Firewall außen]
   |
DMZ: Webserver / Reverse Proxy / Mail-Gateway
   |
[Firewall innen]
   |
LAN: Clients / Dateiserver / Datenbank / Verwaltung
```

Die wichtige Sicherheitsidee ist nicht "DMZ ist sicher". Die wichtige Idee ist:

```text
DMZ ist begrenzt erreichbar und vom LAN getrennt.
```

Wenn ein DMZ-Server angegriffen wird, soll der Schaden in dieser Zone bleiben. Deshalb braucht die DMZ eigene Firewall-Regeln, eigene Updates, Logging, minimale Dienste und klare Adminwege.

---

## Kommunikationsmatrix für eine typische DMZ

| Von | Nach | Erlaubt? | Begründung |
|---|---|---:|---|
| Internet | Webserver-DMZ TCP 443 | ja | Die Website soll erreichbar sein. |
| Internet | LAN | nein | Externe Nutzer dürfen nicht direkt ins interne Netz. |
| DMZ | LAN beliebig | nein | Kompromittierter DMZ-Server darf nicht frei weiter. |
| Webserver-DMZ | Datenbank TCP 5432 | nur wenn nötig | Fachlich benötigte Verbindung eng begrenzen. |
| LAN | Internet | ja, kontrolliert | Mitarbeitende brauchen definierte Internetdienste. |
| Admin-VPN | DMZ-Server SSH/RDP | ja, eng begrenzt | Administration nur über geschützten Zugang. |
| Gast-WLAN | LAN | nein | Gäste müssen getrennt bleiben. |

<Beispiel titel="Online-Shop">
Ein Online-Shop hat einen Reverse Proxy in der DMZ, eine Applikation in einem Servernetz und die Datenbank in einem internen Datenbanksegment. Aus dem Internet ist nur TCP 443 zum Reverse Proxy offen. Der Reverse Proxy darf nur zur Applikation. Die Applikation darf nur zum Datenbankport. Clients und Dateiablagen sind nicht aus der DMZ erreichbar.
</Beispiel>

## Firewall, NAT und Port Forwarding zusammendenken

NAT, Port Forwarding und Firewall-Regeln werden oft verwechselt:

| Thema | Frage | Beispiel |
|---|---|---|
| <Term id="nat">NAT</Term> | Welche Adresse wird übersetzt? | Private LAN-Adresse wird zur öffentlichen Router-Adresse. |
| <Term id="port-forwarding">Port Forwarding</Term> | Wohin geht ein eingehender Port? | WAN TCP 443 -> Webserver-DMZ TCP 443. |
| Firewall | Darf der Verkehr durch diese Grenze? | Internet -> DMZ TCP 443 erlaubt, DMZ -> LAN blockiert. |
| Routing | Welcher Weg wird genommen? | DMZ-Netz und LAN-Netz sind getrennte Subnetze. |
| Dienst | Lauscht die Anwendung wirklich? | Webserver hört auf TCP 443. |

Eine Portweiterleitung ohne passende Firewall-Erlaubnis funktioniert nicht. Eine Firewall-Erlaubnis ohne sicheren Dienst ist gefährlich. Ein Dienst im LAN statt in der DMZ kann die ganze interne Umgebung gefährden.

## Typische Fehlersuche

Wenn eine Verbindung nicht funktioniert, gehst du systematisch vor:

| Schritt | Frage | Beispiel |
|---:|---|---|
| 1 | Stimmt die IP-Adresse? | Ziel ist `10.10.20.15`, Regel zeigt aber auf `10.10.20.51`. |
| 2 | Stimmt der Port und das Protokoll? | TCP 443 ist erlaubt, Dienst nutzt aber TCP 8443. |
| 3 | Gibt es Routing zwischen den Zonen? | DMZ kennt Rückweg ins LAN nicht. |
| 4 | Lässt die Firewall an jeder Grenze durch? | Außen-Firewall erlaubt, Innen-Firewall blockiert. |
| 5 | Blockiert die Host-Firewall? | Linux/Windows-Firewall auf dem Server sperrt den Port. |
| 6 | Lauscht der Dienst? | Webserver läuft nicht oder bindet nur auf `localhost`. |
| 7 | Gibt es Logs? | Firewall-Log zeigt DENY wegen falscher Quelle. |

<Tipp titel="Klare Antwort mit Struktur">
Schreibe nicht nur "Firewall freigeben". Besser: Quelle, Ziel, Protokoll, Port, Richtung und Zweck nennen. Beispiel: `Internet -> Webserver-DMZ, TCP 443, HTTPS zur Website, erlauben`.
</Tipp>

## Typische Fehler

1. **Webserver direkt ins LAN stellen.** Ein öffentlicher Server gehört in eine DMZ oder Serverzone, nicht neben Clients und Dateiserver.
2. **DMZ als besonders sicheres Netz verstehen.** Die DMZ ist bewusst exponiert, aber begrenzt und vom LAN getrennt.
3. **Default Deny vergessen.** Ohne abschliessende Sperrregel bleibt oft mehr offen als gewollt.
4. **ANY-Regeln zu breit setzen.** `DMZ -> LAN ANY ALLOW` zerstört den Sinn der DMZ.
5. **Richtung ignorieren.** `LAN -> Internet` ist nicht dasselbe wie `Internet -> LAN`.
6. **Stateful falsch erklären.** Stateful bedeutet Verbindungsgedächtnis, nicht automatische Inhaltssicherheit.
7. **NAT mit Firewall gleichsetzen.** NAT übersetzt Adressen; Firewall-Regeln steuern Erlaubnis und Blockade.
8. **Adminzugriff direkt freigeben.** RDP, SSH, Router- oder NAS-Adminoberflächen gehören nicht ohne Schutz ins Internet.
9. **Keine Dokumentation pflegen.** Unbekannte Regeln bleiben jahrelang offen, weil niemand mehr ihren Zweck kennt.

## Anwendungsbeispiel

<Beispiel titel="Webserver aus dem LAN herausziehen">
Ein Unternehmen betreibt einen Webserver für Kunden. Der Webserver steht bisher im gleichen LAN wie Clients, Dateiserver und Datenbank. Besser ist eine Trennung in Internet/Außenanbindung, DMZ und internes LAN.
</Beispiel>

**Rechenweg: Begründete Struktur**

**Schritt 1 — Zonen trennen**
Der Webserver oder Reverse Proxy steht in der DMZ. Clients, Dateiserver und Datenbank bleiben im internen LAN oder in eigenen Serversegmenten.

**Schritt 2 — Regeln eng formulieren**
Erlaube `Internet -> Webserver-DMZ, TCP 443` für HTTPS. Blockiere `Internet -> LAN`. Blockiere `DMZ -> LAN` grundsätzlich. Erlaube `Webserver-DMZ -> Datenbank` nur auf dem benötigten Datenbankport, falls diese Verbindung wirklich nötig ist.

**Schritt 3 — Administration absichern**
Adminzugriff erfolgt nur aus Admin-VPN oder Managementnetz, nicht direkt aus dem Internet. Am Ende steht eine Default-Deny-Regel.

**Ergebnis**
Die Struktur ist sicherer, weil ein Angriff auf den öffentlichen Webserver nicht automatisch freien Zugriff auf Clients und interne Server bedeutet.

## Kurzcheck

| Frage | Kurzlösung |
|---|---|
| Was ist der Unterschied zwischen Paketfilter, Stateful Firewall und Application-Layer-Gateway? | Paketfilter prüft Paketmerkmale, Stateful merkt Verbindungszustände, Application-Layer-Gateway prüft Anwendungskommunikation. |
| Warum ist Default Deny sicherer als eine Blocklist? | Nur benötigte Kommunikation wird erlaubt; unbekannte oder vergessene Verbindungen bleiben blockiert. |
| Warum gehört ein öffentlicher Webserver nicht ins normale LAN? | Ein kompromittierter Server dürfte sonst leichter zu Clients, Dateiservern und internen Daten weiterwandern. |
| Welche Angaben gehören mindestens in eine klare Firewall-Regel? | Richtung, Quelle, Ziel, Protokoll, Port, Aktion und Zweck. |
| Warum ist eine Heimrouter-"DMZ", die alle Ports an ein internes Gerät weiterleitet, keine echte Unternehmens-DMZ? | Sie trennt keine Sicherheitszone sauber ab, sondern macht ein internes Gerät breit von außen erreichbar. |
