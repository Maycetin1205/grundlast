# TCP vs. UDP

<MetaBar
  lernfeld="LF 3 / LF 9 - Clients in Netzwerke einbinden und Dienste bereitstellen"

## Was du danach kannst

Nach diesem Kapitel kannst du <Term id="tcp">TCP</Term>, <Term id="udp">UDP</Term>, <Term id="portnummer">Portnummern</Term>, <Term id="socket">Sockets</Term>, Verbindungsaufbau, Zuverlässigkeit, Reihenfolge und typische Dienste sicher unterscheiden. Du kannst erklären, warum HTTPS normalerweise TCP 443 nutzt, warum DNS meistens UDP 53 verwendet, warum VoIP keine alten Pakete nachgeliefert haben will und warum Firewall-Regeln immer Protokoll und Port nennen müssen.

Ausserdem verstehst du, warum TCP und UDP die Grundlage für viele andere Kapitel sind: OSI-Schicht 4, NAT, Port Forwarding, Firewall-Regeln, Webdienste, E-Mail, DNS, DHCP, Streaming, Gaming und Fehlersuche.

## Warum das wichtig ist

IP bringt Pakete von Netz zu Netz. TCP und UDP sorgen auf der Transportschicht dafür, dass Daten bei der richtigen Anwendung auf dem Zielsystem landen. Ein Server kann gleichzeitig HTTPS, SSH und DNS anbieten, weil Ports die Dienste unterscheiden.

In der Praxis musst du ständig entscheiden: Welcher Port muss in der Firewall frei sein? Nutzt der Dienst TCP oder UDP? Ist Paketverlust schlimm oder ist Latenz schlimmer? Warum funktioniert DNS-Abfrage A, aber Zonentransfer B nicht? Warum reicht "Port 53 freigeben" als Aussage nicht aus?

<Analogie>
IP ist die Lieferadresse des Gebäudes. Der Port ist die Zimmernummer. TCP ist ein Paketdienst mit Unterschrift, Sendungsverfolgung und erneuter Zustellung. UDP ist ein schneller Zuruf durch ein Fenster: wenig Aufwand, sofort da, aber ohne Garantie. Beides ist sinnvoll, nur für unterschiedliche Situationen.
</Analogie>

## Grundbegriffe

| Begriff | Bedeutung | Praxisblick |
|---|---|---|
| <Term id="transportschicht">Transportschicht</Term> | OSI-Schicht 4, verbindet Anwendungen Ende-zu-Ende. | TCP und UDP sitzen hier. |
| <Term id="tcp">TCP</Term> | Verbindungsorientiertes Transportprotokoll mit Zustellkontrolle. | Zuverlässig, geordnet, mehr Overhead. |
| <Term id="udp">UDP</Term> | Verbindungsloses Transportprotokoll ohne Zustellgarantie. | Schnell, schlank, Anwendung muss Verluste behandeln. |
| <Term id="portnummer">Portnummer</Term> | Nummer, die einen Dienst oder Prozess auf einem Host adressiert. | HTTP 80, HTTPS 443, DNS 53, DHCP 67/68. |
| <Term id="socket">Socket</Term> | Kombination aus IP-Adresse, Transportprotokoll und Port. | `192.168.10.20:443/TCP` beschreibt einen Endpunkt. |
| <Term id="segment">Segment</Term> | Dateneinheit bei TCP auf Schicht 4. | OSI-PDU: TCP = Segment. |
| <Term id="datagramm">Datagramm</Term> | Dateneinheit bei UDP. | OSI-PDU: UDP = Datagramm. |
| <Term id="three-way-handshake">Three-Way-Handshake</Term> | TCP-Verbindungsaufbau mit SYN, SYN-ACK, ACK. | Hilft, Verbindungsaufbau und Verbindungsfehler zu erkennen. |

## TCP und UDP im Vergleich

| Merkmal | TCP | UDP |
|---|---|---|
| Verbindung | verbindungsorientiert | verbindungslos |
| Aufbau | Three-Way-Handshake vor Daten | kein Verbindungsaufbau |
| Zuverlässigkeit | Bestätigungen, Sequenznummern, Wiederholung | keine automatische Wiederholung |
| Reihenfolge | stellt richtige Reihenfolge her | keine Reihenfolgegarantie |
| Datenstrom | Byte-Strom | einzelne Datagramme |
| Header | mindestens 20 Byte | 8 Byte |
| Latenz | mehr Transportmechanik, dafür kontrolliert | weniger Transportmechanik; echte Latenz hängt von Anwendung und Netz ab |
| Typische Dienste | HTTPS, SSH, SMTP, IMAP, FTP | DNS, DHCP, VoIP, Streaming, Gaming |

<Tipp titel="Merksatz">
TCP ist nicht "sicher" im Sinne von verschlüsselt. TCP ist zuverlässig im Sinne von geordnet, bestätigt und wiederholbar. Verschlüsselung kommt zum Beispiel durch TLS obendrauf.
</Tipp>

## Ports: Wie Anwendungen unterschieden werden

Eine IP-Adresse bringt ein Paket zu einem Host. Der Port bringt es zur richtigen Anwendung auf diesem Host.

```text
Server-IP: 203.0.113.10
TCP 22  -> SSH
TCP 80  -> HTTP
TCP 443 -> HTTPS
UDP 53  -> DNS
```

Wichtig: TCP-Port 53 und UDP-Port 53 sind technisch verschiedene Kommunikationsziele. Eine Firewall-Regel muss deshalb das Transportprotokoll nennen.

| Bereich | Portnummern | Bedeutung |
|---|---:|---|
| Well-known Ports | 0 - 1023 | bekannte Standarddienste, z. B. 80/443/53 |
| Registered Ports | 1024 - 49151 | registrierte Anwendungen und Dienste |
| Dynamic/Private Ports | 49152 - 65535 | kurzlebige Client-Ports, z. B. für ausgehende Verbindungen |

<Beispiel titel="Client ruft eine Website auf">
Ein Client verbindet sich zu `https://example.org`. Der Zielport ist TCP 443. Der Client nutzt aber einen zufälligen Quellport, zum Beispiel TCP 51544. Dadurch kann das Betriebssystem mehrere gleichzeitige Verbindungen unterscheiden.
</Beispiel>

```text
Client: 192.168.10.55:51544/TCP  ->  Webserver: 93.184.216.34:443/TCP
```

Diese Kombination aus Quell-IP, Quellport, Ziel-IP, Zielport und Protokoll ist für Firewalls, NAT und Betriebssysteme extrem wichtig.

## TCP: Verbindungsaufbau und Zuverlässigkeit

TCP baut vor der Datenübertragung eine Verbindung auf. Der bekannte Ablauf heißt <Term id="three-way-handshake">Three-Way-Handshake</Term>:

```text
Client                         Server
  |                               |
  | -------- SYN ---------------> |  Verbindungswunsch
  | <------ SYN-ACK ------------- |  Bestaetigung + eigener Wunsch
  | -------- ACK ---------------> |  Bestaetigung
  |                               |
  | ======= Datenstrom =========> |
```

Danach überträgt TCP Daten als geordneten Byte-Strom. Es nutzt unter anderem:

- Sequenznummern, damit Reihenfolge rekonstruiert werden kann
- Bestätigungen, damit Empfang kontrolliert wird
- Wiederholungen, wenn Daten verloren gehen
- Flusskontrolle, damit Empfänger nicht überfordert werden
- Staukontrolle, damit das Netz nicht unnötig überlastet wird

Das ist ideal für Webseiten, Dateiübertragung, E-Mail, SSH, Datenbanken und viele APIs. Wenn ein Byte fehlt, ist eine Datei kaputt oder eine Anmeldung unvollständig. Dann ist erneute Übertragung richtig.

## UDP: Schnell, schlank, ohne Garantie

UDP sendet Datagramme ohne vorherigen Verbindungsaufbau. Es garantiert nicht:

- dass ein Datagramm ankommt
- dass Datagramme in richtiger Reihenfolge ankommen
- dass doppelte Datagramme verhindert werden
- dass verlorene Datagramme automatisch wiederholt werden

Das klingt schlecht, ist aber oft genau richtig. Bei Sprache, Livestreams oder Spielen ist ein Paket, das 2 Sekunden später nachgeliefert wird, oft wertlos. Lieber fehlt kurz ein Tonfragment, als dass die ganze Verbindung hängt.

UDP ist auch für einfache Anfrage-Antwort-Protokolle praktisch. DNS fragt häufig kurz: "Welche IP hat dieser Name?" Die Antwort ist klein. Dafür reicht UDP meistens. Wird es größer oder spezieller, kann DNS auch TCP nutzen.

## Typische Dienste und Transportprotokolle

| Dienst | Port | Meist TCP/UDP | Merkhilfe |
|---|---:|---|---|
| HTTP | 80 | TCP | Webseiten ohne TLS |
| HTTPS | 443 | TCP | Webseiten mit TLS |
| SSH | 22 | TCP | Adminzugriff, Terminal |
| SMTP | 25 | TCP | Mailtransport zwischen Servern |
| IMAP | 143 / 993 | TCP | Mailabruf, 993 mit TLS |
| POP3 | 110 / 995 | TCP | Mailabruf, 995 mit TLS |
| FTP | 20/21 | TCP | Dateiübertragung, historisch |
| DNS | 53 | UDP und TCP | normale Abfragen meist UDP, Zonentransfer/ große Antworten TCP |
| DHCP | 67/68 | UDP | automatische Netzwerkkonfiguration |
| NTP | 123 | UDP | Zeitsynchronisation |
| VoIP/RTP | dynamisch | meist UDP | Echtzeit-Audio/Video |

<Warnung titel="DNS ist die klassische Falle">
DNS ist nicht einfach "UDP". Normale DNS-Abfragen laufen meistens über UDP 53. DNS kann aber auch TCP 53 nutzen, etwa für Zonentransfers oder wenn Antworten größer sind. In Firewall-Regeln muss man also den konkreten Zweck kennen.
</Warnung>

## Entscheidung: Wann TCP, wann UDP?

| Situation | Besser | Warum |
|---|---|---|
| Datei herunterladen | TCP | Jedes Byte muss korrekt und in Reihenfolge ankommen. |
| Login und Webformular | TCP | Vollständigkeit und Reihenfolge sind Pflicht. |
| SSH-Session | TCP | Eingaben und Ausgaben müssen korrekt ankommen. |
| DNS-Standardabfrage | UDP | Kurze Anfrage, kurze Antwort, wenig Overhead. |
| VoIP-Telefonat | UDP | Echtzeit ist wichtiger als Nachlieferung alter Pakete. |
| Online-Spiel | UDP | Niedrige Latenz ist wichtiger als jedes alte Positionspaket. |
| Livestream | UDP oder TCP je nach Technik | Echtzeit-Streams oft UDP, Web-Streaming häufig TCP/HTTPS. |

Die Entscheidung lautet also nicht "TCP gut, UDP schlecht". Sie lautet:

```text
Brauche ich korrekte, vollstaendige, geordnete Daten?
Oder brauche ich geringe Latenz und kann Verluste tolerieren?
```

## Bezug zu Firewall, NAT und Port Forwarding

Firewall-Regeln müssen mindestens Richtung, Quelle, Ziel, Protokoll und Port sauber angeben.

| Schlechte Aussage | Bessere Aussage |
|---|---|
| "Port 443 freigeben" | `Internet -> Webserver-DMZ, TCP 443, HTTPS erlauben` |
| "DNS erlauben" | `Clients -> DNS-Server, UDP 53 erlauben; TCP 53 bei Bedarf begruenden` |
| "Spielserver freigeben" | `Internet -> Gameserver, UDP 27015, nur notwendiger Port` |
| "Adminzugriff erlauben" | `Admin-VPN -> Server, TCP 22, SSH, keine Freigabe aus dem ganzen Internet` |

Bei NAT und Port Forwarding ist TCP/UDP ebenfalls entscheidend. Eine Weiterleitung für TCP 443 hilft keinem Dienst, der UDP 443 nutzt. Umgekehrt kann ein UDP-Port offen sein, obwohl TCP auf derselben Nummer blockiert ist.

Timeout bedeutet oft: Paket wird unterwegs verworfen oder Antwort kommt nicht zurück. Connection refused bedeutet oft: Zielhost erreichbar, aber dort lauscht kein Dienst oder der Host lehnt aktiv ab. Das ist für Fehlersuche wertvoll.

## Typische Fehler

1. **TCP als verschlüsselt bezeichnen.** TCP ist zuverlässig, nicht automatisch vertraulich. HTTPS nutzt TCP plus TLS.
2. **UDP als unsicher oder falsch bewerten.** UDP ist bewusst schlank und für viele Echtzeit- oder Anfrage-Antwort-Dienste passend.
3. **Portnummer ohne Protokoll nennen.** TCP 53 und UDP 53 sind nicht dasselbe.
4. **DNS nur als UDP lernen.** DNS nutzt meistens UDP, kann aber TCP brauchen.
5. **OSI-Schicht verwechseln.** TCP/UDP sind Schicht 4; IP ist Schicht 3; HTTP/DNS/SMTP sind Schicht 7.
6. **TCP-Handshake mit TLS-Handshake verwechseln.** TCP baut die Transportverbindung auf, TLS schützt danach die Inhalte.
7. **Quellport vergessen.** Clients nutzen kurzlebige Quellports; Server nutzen bekannte Zielports.
8. **"Schneller" falsch verstehen.** UDP hat weniger Overhead, aber die Anwendung muss mit Verlusten selbst umgehen.

## Beispiel: DNS-Regeln sauber formulieren

Ein Unternehmen erstellt Firewall-Regeln für einen DNS-Server. Clients sollen Namen auflösen. Ausserdem soll ein zweiter DNS-Server Zonendaten übertragen.

Für normale Client-Abfragen wird meist `Clients -> DNS-Server, UDP 53` erlaubt. Da DNS auch TCP nutzen kann, kann je nach Umgebung auch `Clients -> DNS-Server, TCP 53` nötig sein. Für Zonentransfers zwischen DNS-Servern ist `DNS-Server A -> DNS-Server B, TCP 53` gezielt zu erlauben.

Die Aussage "Port 53 freigeben" reicht nicht, weil eine Firewall zwischen TCP und UDP unterscheidet und weil Quelle, Ziel, Richtung und Zweck angegeben werden müssen.

## Kurzer Selbstcheck

| Check | Lösung |
|---|---|
| Wichtigster Unterschied zwischen TCP und UDP | TCP baut eine Verbindung auf und liefert einen geordneten, zuverlässigen Byte-Strom. UDP sendet einzelne Datagramme ohne Zustell- und Reihenfolgegarantie. |
| Warum reicht eine Portnummer allein nicht? | TCP 53 und UDP 53 sind unterschiedliche Kommunikationsziele. Eine Regel braucht Protokoll, Port, Quelle, Ziel, Richtung und Zweck. |
| Ablauf des TCP-Verbindungsaufbaus | SYN, SYN-ACK, ACK. Danach kann der Datenstrom laufen. |
| Warum passt UDP zu VoIP? | Echtzeit ist wichtiger als späte Nachlieferung alter Pakete. Kurze Verluste stören weniger als hoher Verzug. |
| Warum ist DNS ein gutes Grenzbeispiel? | Standardabfragen laufen meist über UDP 53, DNS muss aber auch TCP unterstützen und nutzt TCP besonders für größere Antworten oder Zonentransfers. |
