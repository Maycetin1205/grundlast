## Was du danach kannst

Nach diesem Kapitel kannst du erklaeren, was ein <Term id="prozess">Prozess</Term>, ein <Term id="thread">Thread</Term> und ein <Term id="task">Task</Term> ist. Du kannst im Task-Manager oder in Linux-Werkzeugen einschaetzen, warum ein Programm viel CPU, RAM oder I/O verbraucht, warum eine Anwendung "haengt" und warum ein Prozess mehrere Threads haben kann. Ausserdem erkennst du typische Pruefungsfallen: Ein Prozess ist nicht einfach "ein Fenster", ein Thread ist nicht dasselbe wie ein CPU-Kern, und Multitasking bedeutet nicht automatisch echte Parallelitaet.

## Warum das wichtig ist

Ein Betriebssystem muss viele Dinge scheinbar gleichzeitig erledigen: Browser, Virenschutz, Datei-Download, Musik, Druckauftrag, Hintergrundupdates und Eingaben von Maus und Tastatur. Die CPU kann aber pro Kern immer nur eine Ausfuehrungseinheit gleichzeitig bearbeiten. Damit sich das System trotzdem fluessig anfuehlt, verteilt das Betriebssystem Rechenzeit.

Im Betrieb brauchst du dieses Wissen, wenn ein Client langsam ist, ein Serverdienst nicht mehr reagiert oder eine Anwendung dauerhaft 100 Prozent CPU-Last erzeugt. Dann reicht "Programm neu starten" nicht als Erklaerung. Du musst verstehen, welche Einheit Ressourcen besitzt, welche Einheit ausgefuehrt wird und welche Einheit der Benutzer im Werkzeug sieht.

<Analogie>
Stell dir ein Restaurant vor. Das **Programm** ist das Rezept. Der **Prozess** ist eine geoeffnete Kueche mit Zutaten, Geraeten, Budget und eigener Arbeitsflaeche. Die **Threads** sind die Koeche in dieser Kueche: einer schneidet, einer kocht, einer richtet an. Der **Scheduler** ist die Schichtleitung, die entscheidet, welcher Koch wann an den Herd darf. Mehr Koeche helfen nur, wenn genug Herde, Platz und sinnvolle Aufgaben vorhanden sind.
</Analogie>

## Grundbegriffe

| Begriff | Kurz erklaert | Merksatz |
|---|---|---|
| **Programm** | Datei oder Code auf dem Datentraeger, der ausgefuehrt werden kann. | Programm = Bauplan. |
| <Term id="prozess">Prozess</Term> | Laufende Instanz eines Programms mit eigenem Speicherbereich und Ressourcen. | Prozess = Programm in Ausfuehrung plus Ressourcen. |
| <Term id="thread">Thread</Term> | Ausfuehrungsstrang innerhalb eines Prozesses; bekommt CPU-Zeit vom Betriebssystem. | Thread = das, was wirklich laeuft. |
| <Term id="task">Task</Term> | Allgemeiner Aufgabenbegriff; je nach System Werkzeugbezeichnung fuer Prozess, Thread oder geplante Arbeit. | Task = Aufgabe, Kontext beachten. |
| <Term id="scheduler">Scheduler</Term> | Betriebssystem-Komponente, die CPU-Zeit auf Threads/Tasks verteilt. | Scheduler = Zeitverteiler. |
| <Term id="kontextwechsel">Kontextwechsel</Term> | Wechsel der CPU von einem Thread/Task zu einem anderen. | Kontextwechsel kostet Zeit. |

<Tipp titel="Pruefungsmerksatz">
Ein Prozess besitzt Ressourcen. Ein Thread nutzt CPU-Zeit. Der Scheduler verteilt die CPU-Zeit.
</Tipp>

## Prozess vs. Thread

Ein Prozess ist die Schutz- und Ressourcengrenze. Er hat typischerweise eine Prozess-ID, eigenen virtuellen Speicher, geoeffnete Dateien, Netzwerkverbindungen, Rechte und mindestens einen Thread. Wenn du ein Programm startest, erzeugt das Betriebssystem einen Prozess und darin den ersten Thread.

Ein Thread ist leichter als ein Prozess, weil Threads desselben Prozesses viele Ressourcen teilen. Mehrere Threads koennen im gleichen Speicherbereich arbeiten. Das macht Kommunikation schneller, aber auch gefaehrlicher: Wenn zwei Threads gleichzeitig dieselben Daten veraendern, entstehen leicht Fehler.

| Merkmal | Prozess | Thread |
|---|---|---|
| Ressourcen | eigener Adressraum, Handles, Rechte, Umgebung | teilt Prozessressourcen |
| Ausfuehrung | enthaelt mindestens einen Thread | wird vom Scheduler ausgefuehrt |
| Isolation | staerker voneinander getrennt | schwacher getrennt, weil gemeinsamer Speicher |
| Fehlerwirkung | Prozessabsturz betrifft meist diesen Prozess | Threadfehler kann den ganzen Prozess destabilisieren |
| Erstellung | vergleichsweise aufwendig | vergleichsweise leichtgewichtig |
| Beispiel | Browser-Prozess, Datenbankdienst, Druckdienst | UI-Thread, Netzwerk-Thread, Worker-Thread |

## Multitasking, Parallelitaet und CPU-Kerne

<Term id="multitasking">Multitasking</Term> bedeutet, dass ein Betriebssystem mehrere Aufgaben so verwaltet, dass sie fuer den Benutzer gleichzeitig wirken. Auf einem einzigen CPU-Kern passiert das durch schnelles Umschalten. Auf mehreren Kernen koennen wirklich mehrere Threads gleichzeitig laufen.

Wichtig ist die Unterscheidung:

| Situation | Was passiert wirklich? |
|---|---|
| 1 Kern, 10 lauffaehige Threads | Der Scheduler wechselt schnell zwischen Threads. Es wirkt parallel, ist aber zeitlich aufgeteilt. |
| 4 Kerne, 4 lauffaehige Threads | Bis zu vier Threads koennen wirklich gleichzeitig laufen. |
| 4 Kerne, 40 lauffaehige Threads | Einige laufen, der Rest wartet auf CPU-Zeit; viele Kontextwechsel sind moeglich. |
| Thread wartet auf Datei/Netzwerk | Er verbraucht oft keine CPU, sondern wartet auf I/O. |

Ein System mit vielen Threads ist deshalb nicht automatisch schneller. Threads bringen etwas, wenn Arbeit sinnvoll aufgeteilt werden kann, etwa in Benutzeroberflaeche, Netzwerk, Berechnung und Hintergrundaufgaben. Sie bringen wenig, wenn alle Threads auf dieselbe Ressource warten oder sich gegenseitig blockieren.

<Beispiel titel="Betriebliche Situation">
Ein Mitarbeiter meldet: "Mein Warenwirtschaftsprogramm ist abgestuerzt." Im Task-Manager steht der Prozess noch in der Liste, die CPU-Last ist fast 0 Prozent, aber das Fenster reagiert nicht. Das spricht nicht fuer "CPU zu schwach", sondern eher fuer einen blockierten UI-Thread, eine wartende Datenbankabfrage, Netzwerkproblem oder Deadlock. ## Typische Fehler

<Warnung titel="Pruefungs- und Praxisfallen">
1. **Prozess mit Programm verwechseln.** Das Programm liegt als Datei vor; der Prozess ist die laufende Instanz.
2. **Thread mit CPU-Kern verwechseln.** Ein Thread ist eine Ausfuehrungseinheit der Software; ein Kern ist Hardware.
3. **Task immer gleich Prozess setzen.** Task ist ein allgemeiner Begriff. Im Task-Manager wirkt er oft wie Prozess oder App, in Scheduling-Kontexten kann er allgemeiner gemeint sein.
4. **Viele Threads automatisch als schneller bewerten.** Mehr Threads helfen nur, wenn die Arbeit parallelisierbar ist und keine gemeinsame Ressource bremst.
5. **Hohe RAM-Nutzung als CPU-Problem deuten.** RAM, CPU und I/O sind verschiedene Engpaesse.
6. **Prozess sofort hart beenden.** Das kann ungespeicherte Daten verlieren oder Dienste in unsauberen Zustand bringen.
</Warnung>

## Typische Pruefungsaufgabe

> **Aufgabe (Klausur-Stil):** Ein Betriebssystem zeigt fuer eine Anwendung einen Prozess mit acht Threads an. Erklaere den Unterschied zwischen Prozess und Thread. Warum kann die Anwendung trotz acht Threads auf einem Ein-Kern-System nicht acht Dinge wirklich gleichzeitig berechnen?

**Musterantwort:** Der Prozess ist die laufende Instanz eines Programms und besitzt Ressourcen wie Speicherbereich, geoeffnete Dateien, Rechte und Prozess-ID. Ein Thread ist ein Ausfuehrungsstrang innerhalb dieses Prozesses und bekommt CPU-Zeit vom Scheduler. Mehrere Threads eines Prozesses teilen viele Ressourcen des Prozesses.

Auf einem Ein-Kern-System kann zu einem Zeitpunkt nur ein Thread wirklich auf der CPU laufen. Der Scheduler wechselt sehr schnell zwischen lauffaehigen Threads. Dadurch wirkt die Ausfuehrung gleichzeitig, ist aber zeitlich aufgeteilt. Echte parallele Berechnung braucht mehrere CPU-Kerne oder Prozessoren.
