# Port Forwarding und NAT

<MetaBar
  lernfeld="LF 3 / LF 9 - Clients in Netzwerke einbinden und Netzwerke bereitstellen"
/>

## Was du danach kannst

Nach diesem Kapitel kannst du <Term id="nat">NAT</Term>, <Term id="napt">NAPT/PAT</Term>, <Term id="port-forwarding">Port Forwarding</Term>, private und öffentliche IPv4-Adressen unterscheiden. Du verstehst, warum ein Client aus einem privaten Netz ins Internet kommt, warum ein Server hinter einem Heimrouter von außen nicht automatisch erreichbar ist und warum eine offene Portweiterleitung ein Sicherheitsrisiko ist.

Du kannst ausserdem typische Netzwerk- und Betriebssituationen lösen: Webserver hinter NAT freigeben, Remotezugriff bewerten, Firewall-Regeln lesen, Portweiterleitung testen und sichere Alternativen wie VPN oder DMZ einordnen.

## Warum das wichtig ist

Viele Netze verwenden intern <Term id="private-ipv4-adresse">private IPv4-Adressen</Term> wie `192.168.178.0/24` oder `10.0.0.0/8`. Diese Adressen sind im Internet nicht global eindeutig. Dein Router oder deine Firewall übersetzt deshalb beim Zugriff nach draußen interne Adressen in eine öffentliche Adresse. Genau hier beginnt NAT.

Im Alltag wirkt das unsichtbar: Notebook, Smartphone und Drucker nutzen alle denselben Internetanschluss. Sobald aber ein Dienst von außen erreichbar sein soll, wird es ernst. Dann musst du entscheiden: Brauchen wir wirklich Port Forwarding? Steht der Dienst sicher genug? Gibt es eine bessere Lösung über VPN, Reverse Proxy, Cloud-Dienst oder DMZ?

<Analogie>
NAT ist wie der Empfang eines Unternehmens. Intern haben alle Mitarbeitenden Durchwahlnummern, nach außen sieht man aber zuerst nur die Hauptnummer. Ruft ein Mitarbeiter hinaus, merkt sich der Empfang, welche interne Durchwahl zu welchem Gespräch gehört. Port Forwarding ist eine feste Regel: "Anrufe auf Durchwahl 443 von außen bitte direkt zum Webserver im Raum 12 weiterleiten."
</Analogie>

## Grundbegriffe

| Begriff | Bedeutung | Praxisblick |
|---|---|---|
| <Term id="private-ipv4-adresse">Private IPv4-Adresse</Term> | Adresse aus RFC-1918-Bereichen, nur für interne Netze gedacht. | Nicht global geroutet. |
| <Term id="öffentliche-ipv4-adresse">Öffentliche IPv4-Adresse</Term> | Global eindeutige IPv4-Adresse, im Internet routbar. | Wird vom Provider zugeteilt oder über Provider-/Cloud-Infrastruktur genutzt. |
| <Term id="nat">NAT</Term> | Network Address Translation: IP-Adressen werden zwischen Adressräumen übersetzt. | Typisch zwischen privatem LAN und Internet. |
| <Term id="napt">NAPT/PAT</Term> | Network Address Port Translation: Adresse und Port werden übersetzt. | Viele interne Geräte teilen sich eine öffentliche IPv4-Adresse. |
| <Term id="port-forwarding">Port Forwarding</Term> | Eingehende Verbindung auf einem externen Port wird an internes Ziel weitergeleitet. | Macht interne Dienste von außen erreichbar. |
| <Term id="firewall-regel">Firewall-Regel</Term> | Erlaubt oder blockiert Verkehr nach Quelle, Ziel, Protokoll, Port und Richtung. | Portweiterleitung ohne passende Firewall-Regel bringt nichts oder ist unsicher. |
| <Term id="dmz">DMZ</Term> | Separates Netzsegment für Systeme, die von außen erreichbar sein müssen. | Schützt das interne LAN, wenn ein öffentlicher Server angegriffen wird. |

## Private und öffentliche IPv4-Adressen

RFC 1918 definiert drei private IPv4-Bereiche:

| Bereich | CIDR | Typischer Einsatz |
|---|---:|---|
| `10.0.0.0` - `10.255.255.255` | `10.0.0.0/8` | große Unternehmensnetze |
| `172.16.0.0` - `172.31.255.255` | `172.16.0.0/12` | mittlere interne Netze |
| `192.168.0.0` - `192.168.255.255` | `192.168.0.0/16` | Heimnetze, kleine Standorte, Labore |

Private Adressen dürfen mehrfach vorkommen. Zwei Firmen können beide intern `192.168.10.0/24` verwenden. Im Internet wäre das unmöglich, weil Router dann nicht eindeutig wüssten, wohin Pakete gehören. Darum werden private Adressen im Internet nicht normal geroutet.

Eine öffentliche IPv4-Adresse ist dagegen global erreichbar, sofern Routing und Firewall es erlauben. Bei einem typischen Heimanschluss hat der Router eine öffentliche Adresse am WAN-Anschluss und private Adressen im LAN.

```text
Internet
  |
  | öffentliche IPv4: 203.0.113.25
[Router/NAT]
  | private IPv4: 192.168.178.1
  |
LAN: 192.168.178.0/24
  - Notebook: 192.168.178.20
  - Smartphone: 192.168.178.21
  - NAS: 192.168.178.50
```

<Tipp titel="Typische Falle">
`192.168.x.x`, `10.x.x.x` und `172.16.x.x` bis `172.31.x.x` sind private Adressen. `172.15.x.x` und `172.32.x.x` gehören nicht zum privaten RFC-1918-Bereich. Das wird gerne als kleine Falle eingebaut.
</Tipp>

## NAT beim Zugriff nach draußen

Beim normalen Surfen startet der Client im privaten Netz die Verbindung. Der NAT-Router ersetzt die interne Quelladresse durch seine öffentliche Adresse und merkt sich in einer Tabelle, welcher interne Client zu welcher Verbindung gehört.

<StepByStep titel="Client ruft eine Website auf">
  <Schritt nr={1} titel="Client startet Verbindung">
    <p>Das Notebook `192.168.178.20` verbindet sich per TCP zu `198.51.100.10:443`.</p>
  </Schritt>
  <Schritt nr={2} titel="Router übersetzt nach außen">
    <p>Der Router ersetzt die private Quelladresse durch seine öffentliche Adresse. Bei NAPT/PAT wird zusätzlich ein Quellport verwendet, damit viele Clients unterscheidbar bleiben.</p>
    <pre><code>{`Vor NAT:  192.168.178.20:51544 -> 198.51.100.10:443
Nach NAT: 203.0.113.25:62001   -> 198.51.100.10:443`}</code></pre>
  </Schritt>
  <Schritt nr={3} titel="Antwort kommt zurück">
    <p>Die Website antwortet an `203.0.113.25:62001`. Der Router findet den passenden Tabelleneintrag.</p>
  </Schritt>
  <Schritt nr={4} titel="Router übersetzt nach innen">
    <p>Der Router ersetzt das Ziel wieder durch `192.168.178.20:51544` und leitet das Paket ins LAN.</p>
  </Schritt>
  <Ergebnis>
    <p>Der Client kann ins Internet, obwohl seine private Adresse dort nicht geroutet wird.</p>
  </Ergebnis>
</StepByStep>

Die wichtigste Idee: Normales NAT für ausgehende Verbindungen ist zustandsbehaftet. Der Router merkt sich gestartete Verbindungen. Eine zufällige neue Verbindung aus dem Internet hat aber keinen passenden Eintrag und wird verworfen, sofern keine Portweiterleitung oder passende Regel existiert.

## NAT, NAPT/PAT und Port Forwarding sauber trennen

| Technik | Richtung | Was passiert? | Beispiel |
|---|---|---|---|
| NAT allgemein | innen nach außen oder zwischen Netzen | IP-Adresse wird übersetzt. | `192.168.178.20` wird zu `203.0.113.25`. |
| NAPT/PAT | meist innen nach außen | IP-Adresse und Port werden übersetzt. | Viele Clients teilen sich eine öffentliche IPv4. |
| Statisches NAT | fest definierte Zuordnung | Eine interne Adresse wird dauerhaft einer externen Adresse zugeordnet. | Server `10.0.0.10` nutzt immer externe Adresse `198.51.100.10`. |
| Port Forwarding | außen nach innen | Externer Port wird an interne IP und internen Port weitergeleitet. | `203.0.113.25:443` -> `192.168.178.50:443`. |

Im Sprachgebrauch sagen viele einfach "NAT", obwohl sie NAPT/PAT meinen. Fachlich ist das wichtig: Ohne Portübersetzung könnte nicht ohne Weiteres eine ganze Wohnung oder ein ganzes Büro gleichzeitig über eine einzige öffentliche IPv4-Adresse surfen.

## Port Forwarding: Server hinter dem Router erreichbar machen

Ein NAS im LAN hat die private Adresse `192.168.178.50` und bietet HTTPS auf Port `443` an. Von innen funktioniert der Zugriff. Von außen nicht, weil das Internet keine Route zu `192.168.178.50` hat.

Mit Port Forwarding wird auf dem Router eine feste Regel eingerichtet:

| Externe Adresse | Externer Port | Protokoll | Internes Ziel | Interner Port |
|---|---:|---|---|---:|
| `203.0.113.25` | `443` | TCP | `192.168.178.50` | `443` |

Danach gilt:

```text
Internet-Client -> 203.0.113.25:443
Router          -> 192.168.178.50:443
NAS/Webserver   -> antwortet über Router zurück
```

<Warnung titel="Port Forwarding ist keine Sicherheitsmassnahme">
Port Forwarding macht einen Dienst erreichbar. Es schützt ihn nicht. Sicherheit entsteht durch minimale Freigaben, aktuelle Software, starke Authentifizierung, TLS, Firewall-Regeln, Logging, Updates und gute Netztrennung.
</Warnung>

Wenn ein Dienst nur für Mitarbeitende erreichbar sein soll, ist Port Forwarding oft die falsche erste Idee. Besser ist häufig ein VPN: Erst authentifizieren, dann intern zugreifen. Auch ein Reverse Proxy mit TLS, MFA und klaren Zugriffskontrollen kann sinnvoll sein. Bei öffentlichen Servern gehört der Dienst nicht ungeschützt ins normale LAN, sondern in eine DMZ oder eine sauber getrennte Serverzone.

## Firewall-Regeln und NAT-Regeln zusammen denken

In vielen Systemen sind NAT-Regel und Firewall-Regel getrennt. Die NAT-Regel sagt, wohin ein Paket übersetzt wird. Die Firewall-Regel sagt, ob es überhaupt erlaubt ist.

| Regeltyp | Frage | Beispiel |
|---|---|---|
| NAT/Portweiterleitung | Wohin soll das Paket technisch umgeschrieben werden? | WAN TCP 443 -> `192.168.178.50:443` |
| Firewall | Darf dieses Paket durch? | Erlaube Internet -> NAS TCP 443 |
| Server-Firewall | Nimmt der Zielserver den Verkehr an? | Windows/Linux-Firewall erlaubt TCP 443 |
| Anwendung | Lauscht der Dienst wirklich? | Webserver bindet auf `0.0.0.0:443` oder passender IP |

Fehlt eine dieser Ebenen, klappt der Zugriff nicht. Deshalb reicht "Port ist freigegeben" als Fehlerbeschreibung nicht.

<Beispiel titel="Fehlerfall aus dem Betrieb">
Ein Kunde will von unterwegs auf eine Kamera zugreifen. Intern ist sie unter `192.168.1.80:8080` erreichbar. Im Router ist aber eine Weiterleitung auf `192.168.1.60:80` eingetragen. ## Sicherheitsbewertung: Wann ist Port Forwarding vertretbar?

| Situation | Bewertung | Bessere oder notwendige Maßnahmen |
|---|---|---|
| Öffentliche Website | vertretbar, wenn geplant | Webserver in DMZ/Servernetz, TLS, Updates, Logging, Reverse Proxy |
| NAS-Verwaltung ins Internet freigeben | meist riskant | VPN, MFA, keine Admin-Oberfläche direkt ins Internet |
| RDP/SSH direkt ins Internet | kritisch | VPN, Bastion Host, IP-Restriktion, MFA, starke Schlüssel, Fail2ban/Monitoring |
| Spielserver für Freunde | möglich, aber bewusst | nur notwendiger Port, getrenntes System, Updates, keine Adminfreigaben |
| IoT-Kamera von außen | häufig riskant | VPN oder Herstellerlösung bewerten, Firmware-Updates, eigenes VLAN |

<Tipp titel="Gute Antwort">
Eine starke Antwort nennt nicht nur "Port freigeben", sondern auch die Gegenmassnahmen: nur notwendige Ports, Zielsystem patchen, starke Authentifizierung, Firewall einschränken, DMZ/VLAN nutzen, Logs überwachen und VPN als Alternative prüfen.
</Tipp>

## Carrier-Grade NAT und DS-Lite

Nicht jeder Internetanschluss hat eine eigene öffentliche IPv4-Adresse am Router. Bei <Term id="carrier-grade-nat">Carrier-Grade NAT</Term> teilen sich mehrere Kunden beim Provider öffentliche IPv4-Adressen. Bei DS-Lite hat der Kunde oft IPv6 nativ, während IPv4 über Provider-Infrastruktur getunnelt oder übersetzt wird.

Folge:

```text
Wenn dein Router keine eigene öffentliche IPv4 am WAN hat,
funktioniert klassisches eingehendes IPv4-Portforwarding nicht wie erwartet.
```

Mögliche Lösungen:

- echte öffentliche IPv4 beim Provider buchen, falls verfügbar
- IPv6 sauber nutzen und per Firewall absichern
- VPN mit ausgehend aufgebautem Tunnel verwenden
- Cloud-Relay oder Reverse Tunnel bewusst einsetzen
- Dienst in ein Rechenzentrum oder in die Cloud verlagern

Wichtig: IPv6 braucht normalerweise kein NAT für Adressknappheit. Das bedeutet aber nicht "alles ist offen". Sicherheit wird dann noch stärker über Firewall-Regeln, Segmentierung und sichere Dienste hergestellt.

---

## Typische Fehler

1. **Private Adresse als Internetadresse verwenden.** `192.168.178.50` ist aus dem Internet nicht direkt erreichbar.
2. **NAT als Firewall missverstehen.** NAT kann eingehende Pakete ohne Zustand faktisch abweisen, ersetzt aber keine Sicherheitsarchitektur.
3. **Port Forwarding ohne Zielschutz setzen.** Ein ungepatchter Dienst bleibt ungepatcht, nur jetzt weltweit erreichbar.
4. **TCP und UDP verwechseln.** Eine TCP-Regel hilft keinem Dienst, der UDP braucht.
5. **Interne IP per DHCP wechseln lassen.** Die Weiterleitung zeigt dann irgendwann auf ein anderes Gerät.
6. **Admin-Oberflächen freigeben.** Router-, NAS- oder Kameraverwaltung direkt im Internet ist fast immer eine schlechte Idee.
7. **DS-Lite/CGNAT ignorieren.** Ohne eigene öffentliche IPv4 kommt eingehendes IPv4 nicht sauber bis zum Router.
8. **DMZ im Heimrouter falsch verstehen.** Manche Router nennen "DMZ" eine Weiterleitung aller Ports an ein internes Gerät. Das ist keine echte Unternehmens-DMZ.

## Anwendungsbeispiel

<Beispiel titel="Webserver hinter NAT veröffentlichen">
Ein Kleinunternehmen betreibt einen Webserver intern unter `192.168.10.20`. Der Router hat die öffentliche IPv4 `198.51.100.44`. Die Website soll per HTTPS aus dem Internet erreichbar sein.
</Beispiel>

<StepByStep titel="Sichere Portweiterleitung begründen">
  <Schritt nr={1} titel="Weiterleitung formulieren">
    Leite am WAN `198.51.100.44`, TCP-Port `443`, auf das interne Ziel `192.168.10.20`, TCP-Port `443`, weiter.
  </Schritt>
  <Schritt nr={2} titel="Erlaubnis prüfen">
    Router-Firewall und Server-Firewall müssen eingehenden HTTPS-Verkehr erlauben. Der Webserver muss auf TCP 443 lauschen.
  </Schritt>
  <Schritt nr={3} titel="Schutz ergänzen">
    Der Server gehört in eine DMZ oder ein getrenntes Servernetz. Nur notwendige Ports werden freigegeben; TLS, Updates, starke Authentifizierung, Logging und kein direkter Adminzugang aus dem Internet gehören dazu.
  </Schritt>
  <Ergebnis>
    `192.168.10.20` ist eine private RFC-1918-Adresse und wird im Internet nicht global geroutet. Der Zugriff von außen funktioniert deshalb über die öffentliche Adresse des Routers und eine passende Portweiterleitung.
  </Ergebnis>
</StepByStep>
